# db-workflow — notes (step 2.5)

Schema `workflow`, owned by workflow-service — the configurable approval engine (4.7). Diagram: [db-workflow.drawio](db-workflow.drawio).

## Key decisions
- **Definition / instance split with pinned versions**: `workflow_definition.version_no` + partial unique `(document_type_id) WHERE is_active` (one active per doc type). Instances pin `definition_id`, so an admin edit mid-flight never mutates a running approval. Admin "edit" = insert new definition version + flip `is_active`, gated by permission `workflow:configure` (registry §6/§10 — not a schema concern here). Endpoints (seq-08): `GET|POST /workflow-definitions`, `PUT /workflow-definitions/{id}/steps` (rejected unless `is_active = false` — an active version is read-only), `POST /workflow-definitions/{id}/activate`. **The step edit takes the same row lock as the activation swap**: `SELECT … WHERE id = :target FOR UPDATE`, then re-check `is_active = false` *under the lock* and replace the `workflow_step_definition` rows in that same transaction. Checking `is_active` outside a transaction and writing after leaves a window where a concurrent activation commits in between and the edit mutates a now-active chain — a change to the live approval path with no version bump and no activation, which is what the version-then-activate model exists to prevent. Locking the same row makes the two writers serialize: the loser gets `FAILED_PRECONDITION`, or the activation finds the steps already final. **The activation swap is one transaction and needs guards, not just ordering**: `SELECT … FOR UPDATE` the target and assert it exists; its own `document_type_id` defines the swap scope. If it is already active, return an idempotent `200` after a read-only commit, with no duplicate audit record. Otherwise deactivate the incumbent (0 or 1 rows — 0 is the legitimate first-activation case), then require the target activation to report **exactly 1 row**, else `ROLLBACK`. Without that last count a deactivate can commit unpaired with its activate, leaving the document type with **no** active definition and every subsequent submit failing `ValidateStartable` with no error raised at the moment of damage. Concurrent activations serialize on the incumbent row and the loser aborts on the partial unique.
- **Not a BPMN engine**: ordered sequential steps only. **Parallel approval is out of scope** — no requirement backs it and Figma shows only "Parallel: No"; noted so nobody adds a column speculatively.
- **Conditional steps — considered and cut**: Figma's admin builder showed a condition ("Sales Manager · value > 1B") on Contract's since-removed Commercial approval step. Once that step was dropped (simplification: CONTRACT is now Sales review → Legal review → Director sign-off, 3 steps, no value threshold), no seed chain in registry §7 has a conditional step left — so `condition_expr`, the `SKIPPED` step status, and the `document_value` instance snapshot that only fed it were all removed from the schema rather than kept unused. Configurable, data-driven steps (4.7) don't require conditional *execution*; re-add all three together if a specific document type later needs this as a deliberate technical demonstration.
- **D4 double-submit — two constraints, two different jobs, both required**: `idempotency_key uuid NOT NULL UNIQUE` (permanent, no status scoping) is what makes *retrying the same dispatch attempt* idempotent — the caller's outbox row generates this key exactly once at creation and every retry of that row (the owning dispatcher, a reclaiming worker, or the recovery path in registry §6's stale-claim handling) reuses it unchanged, so `StartInstance` always resolves to the same instance **no matter its current status**, including CANCELLED. This is the piece the partial index alone can't provide: `(document_type_code, document_id) WHERE status='IN_PROGRESS'` only blocks a second instance while the first is still active — once an instance moves past IN_PROGRESS (e.g. cancelled by registry §6's recovery flow), that partial index no longer sees it, so a paused worker resuming with the *same* key would otherwise be free to create a second, live instance for a document already resolved. The permanent `idempotency_key` constraint is what closes that gap; the partial index still does its own, separate job — rejecting *concurrent, differently-keyed* submissions (a true double-submit from the UI) while an instance is genuinely in progress. Neither replaces the other.
- **D5 approve race**: `workflow_step_instance.version` optimistic lock — the action UPDATE carries `WHERE id=? AND version=? AND status='ACTIVE'`; the concurrent loser gets 0 rows and an `ABORTED` (REST callers see 409), and the `status='ACTIVE'` predicate (not the version alone) is what rejects actions on completed or pending steps (APR-02).
- **Cancellation**: `WorkflowInternal.CancelInstance(document_type, document_id, idempotency_key)` (registry §5), called by the owner service inside its document-cancel flow (retried on `UNAVAILABLE`, APR-07 spirit). **Looked up by `idempotency_key`, not `instance_id`** — the caller (mid-way through registry §6's cancel/dispatch handoff) may not have an `instance_id` yet, since not knowing whether one exists is exactly the ambiguity being resolved; `idempotency_key` is always available (read off the caller's own outbox row) and is unique on `workflow_instance`, so the lookup is exact regardless. Succeeds only while no step has been actioned (`FAILED_PRECONDITION` otherwise); sets instance → CANCELLED, the ACTIVE step → CANCELLED via the same version-guarded UPDATE (closing the approve-vs-cancel race), and all PENDING steps → CANCELLED. The same PENDING→CANCELLED sweep runs when an instance terminates early (REJECTED / REVISION_REQUESTED). No `instance_cancelled` event — inbox queries reflect the state immediately.
- **Resolution timing, made explicit**: `step_assignee` for **every** step in the chain — not just the first — is populated in one pass in the instance-creation transaction, by calling identity once per distinct role. This is deliberate, not lazy per-step resolution at activation: resolving the whole chain upfront is what lets a missing assignee on step 3 fail the submission immediately, instead of only surfacing after steps 1–2 are already approved.
- **Empty assignee resolution**: if any step's role resolves to zero users at that instance-creation pass, the submit fails with a clear error (admin must fix role assignments) — no instance is created, nothing strands. Identity's `IdentityInternal.ListUsersByRole` returns `status='ACTIVE'` users only (registry §5), so a role whose every holder is `DISABLED` resolves to zero and hits this same safeguard, rather than silently assigning a step to someone who can never act on it.
- **APR-01 contextual auth**: `step_assignee` rows are the **snapshot of who may act**, resolved from identity (`IdentityInternal.ListUsersByRole`) at instance creation (see above — not at step activation, which only flips `workflow_step_instance.status` to `ACTIVE` for whichever step is next). At instance creation, all `ACTIVE` users holding the configured step role are snapshotted into `step_assignee`. Only users in this snapshot may act; possessing the role later is insufficient. Disabled users and users granted the role after instance creation cannot act. This gives APR-01 meaningful contextual enforcement:
  - Role holder but not in snapshot → denied
  - Snapshotted assignee on an inactive/completed step → denied
  - Snapshotted assignee on the current ACTIVE step → allowed

  No per-step user override (`approver_user_id` was considered and cut — registry §7 chains are role-only, nothing backs it). Inbox tabs: **Assigned to me** = ACTIVE steps where caller ∈ `step_assignee`; **Submitted by me** = instances where `requested_by` = caller; **Completed** = caller's past `workflow_action` rows. No **Team queue** tab (dropped — see Figma discrepancies below); one consequence stated plainly: a user granted the role *after* an instance's step already activated has no way to see or act on that step. Accepted — nothing requires live reassignment, and building visibility for it would need the same claim/reassign machinery the drop is avoiding.
- **APR-01 scope limitation, documented honestly**: per-manager document ownership is **not modeled**, because the requirements do not define document-to-manager assignment — no account/document-manager ownership concept, no assignee-selection algorithm, no UI for choosing a manager, and no per-step assignment strategy exist anywhere in requirement.md, UC v2, Figma, or the registry. Therefore, when a step's role resolves to more than one active user (e.g. two Legal Reviewers), **all of them** are valid assignees — the first valid action completes the step; concurrent actions are protected by optimistic locking (D5), not by narrowing to one specific person. This is a **documented interpretation** of the ambiguous contextual-authorization line in req §5.5 ("Manager A không được duyệt hồ sơ của Manager B nếu không phải assignee của bước hiện tại") — not a claim that req §5's general "nhóm được phép điều chỉnh" permission covers it (that sentence is specifically about adjusting the provided state-machine diagrams, D14, not about interpreting ambiguous authorization rules). Adding real per-manager ownership (e.g. a `customer.account_manager_id` restricting only the `SALES_MANAGER` steps to one specific user) would introduce a new business concept across schema, API, Figma, workflow resolution, and tests — a scoped later extension if the instructor confirms "Manager B's hồ sơ" means explicit account ownership, not something to introduce speculatively now.
- **APR-03**: `workflow_action.comment` + `CHECK (action = 'APPROVE' OR (comment IS NOT NULL AND comment <> ''))`.
- **Instance snapshots** (`document_no`, `customer_name`, `priority`): make the Approvals Inbox renderable without querying owner services and feed event payloads (D7). `priority` from Figma (LOW/NORMAL/HIGH/URGENT). No `document_value` snapshot — its only reader was `condition_expr` (dropped above), and no Figma screen shows a value column in the inbox.
- **E-sign is not a step** (D10 / 5.5): the Figma builder's "E-signature" card maps to `document_type_config.esign_enabled` + provider config; the engine ends at final approval (APR-05).
- **SLA**: `sla_hours` on step definition (snapshot onto step instance); scheduler emits `workflow.step_overdue` once per step (`overdue_notified_at` stamp prevents re-fire spam). Feeds Figma "Approval overdue" notification + dashboard "4 overdue".
- **Outbox (D6)**: all `workflow.*` lifecycle events are written to `outbox` in the same transaction as the state change.
- `workflow_action` doubles as the approval-history display (Figma "Approval History" tab) — it is **domain data**, not audit: it is the record of who holds/held the document (4.7 "hiển thị người đang xử lý"), served synchronously and never eventually consistent. Audit of config changes (definitions, steps) and of approval actions goes out as `audit.recorded` on the same `outbox` (D15).

## Rule / requirement mapping
| Rule | Design element |
|---|---|
| 4.7 configurable, no hard-code | definitions + steps as data; seed chains registry §7; admin versioning/activation flow in seq-08 (`workflow:configure`) |
| 4.7 progress display | instance `current_step_order` + step statuses (`WorkflowInternal.GetInstanceByDocument`, §5); drawn in seq-03 behind the owner's `GET /<documents>/{id}/progress`. Selection is defined because a document may hold several terminal instances (revise/resubmit ⇒ new `idempotency_key` ⇒ new instance): `IN_PROGRESS` if one exists — at most one, by the partial unique — else latest `created_at DESC` |
| APR-01 | `step_assignee` snapshot + membership check |
| APR-02 | sequential activation + optimistic lock |
| APR-03 | comment CHECK |
| APR-04 | terminal outcome per registry §9 (REJECTED or REVISION_REQUESTED) |
| APR-05 | final approve → instance APPROVED → `workflow.completed` outbox event |
| 5.5 double submit / race | D4 `idempotency_key` UNIQUE (same-attempt retries, any status) + partial unique (concurrent different-key submissions, IN_PROGRESS only) / D5 version column |

## Figma adoptions / discrepancies
- Adopted: step names, SLA, priority, inbox tabs (Assigned to me / Submitted by me / Completed — queries over these tables).
- Discrepancy: drag-reorder = `step_order` updates on a **new** definition version.
- Dropped: Figma's **Team queue** tab. Not in requirement.md or UC v2, not needed to satisfy APR-01 (which requires excluding non-assignees, not adding a broader role-pool view), and it would have surfaced tasks the viewer isn't actually the assignee of — no claim/reassign or view-only logic added to compensate.
- Dropped: Contract's **Commercial approval** step + its "value > 1B" condition. Simplifies CONTRACT to 3 steps (Sales review → Legal review → Director sign-off), matching Contract Detail's approval panel (which never showed this step, and turns out to have been right — see registry change log). The Administration workflow builder screen needs the step card removed and Document Types' Contract step count updated 4 → 3.
- Corrected in the same Administration panel: "Start E-signature" said "Triggered automatically when Final approval completes," directly contradicting D10 (manual send by the document owner, never event-triggered) — reworded to "Available after final approval · Started manually by document owner." Step 1 "Sales review" showed `Role: Sales Officer` against registry §7's `SALES_MANAGER` — corrected. Document Types' step counts for Addendum/Price List/Payment Statement (4/3/4) were stale against their registry §7 chains (2 each) — all corrected to 2; Contract's 3 was already right.

## Constraints & indexes (not shown in the diagram)
- Partial UNIQUE: `workflow_definition (document_type_id) WHERE is_active`; `workflow_instance (document_type_code, document_id) WHERE status = 'IN_PROGRESS'` (D4 — concurrent different-key submissions only).
- UNIQUE: `workflow_instance.idempotency_key` (`NOT NULL` — D4, permanent, status-independent; this is the constraint that makes retries of one dispatch attempt safe forever, see Key decisions), `workflow_definition (document_type_id, version_no)`, `workflow_step_definition (definition_id, step_order)`, `workflow_step_instance (instance_id, step_order)`, `document_type_config.code`.
- CHECK: `workflow_action.action = 'APPROVE' OR (comment IS NOT NULL AND comment <> '')` (APR-03); statuses/priority vs registry §3.
- Optimistic locking: `workflow_step_instance.version` (D5).
- Snapshots (D7): instance `document_no`, `customer_name`, `requested_by_name`; step `name`, `approver_role`, `sla_hours`; `step_assignee.user_name`.
