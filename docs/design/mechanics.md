## M1 — Permission cache (D11)

Context: the JWT carries `roles[]`, never `permissions[]`; the cache is how a role's permission set reaches a running service.

**Permissions are not a claim** — services resolve `roles[] → permissions[]` from a Redis-cached map. A `permissions[]` claim would go stale until re-login; a per-request identity call would sit on the hot path. Fully specified (this map is the *only* path from `role_permission` to a running service, so under-specifying it recreates the original permission-propagation gap in a new place):

- **Writer**: identity-service only — sole owner of `role_permission`, sole writer of the derived cache. No other service writes this namespace.
- **Key/shape**: one key per **role** (not per user — the map is small and role-keyed, so one write updates every holder at once), `perm:role:{role_code}` → JSON array of permission codes.
- **Refresh isn't only change-triggered — it's periodic, or the TTL alone is a scheduled outage.** A rewrite-on-change-only design silently expires the key after one idle TTL window with *no* trigger to ever rewrite it again (roles are edited rarely — realistically not every day), which fails every permission check system-wide until, by coincidence, an admin happens to edit that exact role. So: **identity warms every role's key on startup** (writes all seed roles' keys before serving traffic — no cold-start gap), and **identity also rewrites every role's key on a fixed schedule, every 1h**, regardless of whether anything changed (the same scheduler shape as D9's expiry-warning job and D14d's time-driven status flips — nothing new). Change-triggered rewrite (below) still exists for near-immediate revocation on the common path; the hourly sweep is what bounds it when that write is missed, and what makes the *absence* of a change safe too. Net guarantee is **bounded eventual revocation**, not a hard immediacy promise — nothing in the requirement demands the latter.
- **TTL = 6h** (6× the 1h refresh interval — several consecutive missed sweeps tolerated before anything actually expires; if the scheduler is down that long, other symptoms surface first). TTL is the last-resort self-heal (same philosophy as D9), not the primary mechanism — the periodic sweep is.
- **Invalidation**: in the same admin request that commits a `role_permission` change ("Phân quyền" UC), identity-service immediately overwrites that role's key with the recomputed set — best-effort, not transactional with Postgres (a crash between the two is covered by the next hourly sweep, at most 1h later, not the full TTL window). `user_role` changes (assigning a role to a user) need no Redis write at all — the JWT's `roles[]` claim already carries the user's current roles as of last login/refresh.
- **Redis unavailable → fail closed**: `PERMISSION_DENIED`, never a permissive default — a permission check is an authorization boundary (D11), and the asymmetry from D9's self-heal is deliberate (a missed expiry warning costs nothing, a wrongly-granted permission is a security incident). This doesn't add a new single point of failure: Redis is already load-bearing for JWT blacklist checks (req §6), so it's already a hard dependency for auth.

## M2 — Outbox relay, dispatch and cancellation (D4, D6)

Context: the shared `outbox` shape and its lifecycle summary are in registry §6. Below is the exact relay protocol and the cancel-vs-dispatch handoff — the part that took two corrections to get right (see the registry change log, 2026-07-25 entries).

Relay: poll `WHERE published_at IS NULL AND cancelled_at IS NULL AND (claimed_at IS NULL OR claimed_at < now() - interval 'N seconds') ORDER BY created_at`, **claim** with the *same* predicate — `UPDATE ... SET claimed_at = now() WHERE id = ? AND published_at IS NULL AND cancelled_at IS NULL AND (claimed_at IS NULL OR claimed_at < now() - interval 'N seconds')` (0 rows affected means a concurrent worker already (re)claimed, published, or cancelled it first — under READ COMMITTED the loser's `WHERE` re-evaluates against the winner's already-committed row and correctly fails, so this is a real mutual-exclusion claim, not just an in-memory check). The claim query must match the poll's staleness clause exactly — checking only `claimed_at IS NULL` at claim time (dropping the `OR claimed_at < now() - interval 'N seconds'` half) would make the poll's reclaim window undoable in practice: a row a crashed worker claimed and never finished would keep satisfying the poll's `SELECT` forever but the claim `UPDATE` would never actually match it, stuck permanently. Then act, then stamp `published_at` on success — for a broker publish, only after the Kafka ack (`acks=all`, `enable.idempotence=true`, D2), never on send-call return — or clear `claimed_at` + increment `retry_count` on failure (clearing on failure isn't even load-bearing for correctness, since the same staleness clause reclaims it either way — it just avoids waiting out the full window on a *known* failure). **Ordering constraint the broker cannot supply (D2).** Kafka preserves per-partition order of what the producer *sent*, so per-document commit order survives to the consumer only if this relay sends in commit order. Two properties give that, and both are requirements on the relay rather than on Kafka: the poll is `ORDER BY created_at`, and **one publisher runs per service**. The claim protocol below exists for crash recovery and for the safety of a second instance that starts during a rolling restart — *not* to publish in parallel: two workers each claiming a different row of the same `aggregate_id` can reach the broker in either order, and Kafka will faithfully preserve the wrong one. Deliberately not solved with a per-aggregate lock or a partition-affinity assignment (both real designs, both disproportionate here): the relay is a scheduled task on a service that runs as one instance, and the single consumer chain that depended on ordering was instead made order-tolerant (registry §9 footnote ¹). A stale-claim recovery (below) publishes out of band, but only ever for `workflow.start_requested`, whose target is a gRPC call rather than the broker — so it cannot perturb topic order.

**At-least-once** — consumers dedup via `processed_event` or a natural PK. Lifecycle: `PENDING (claimed_at, published_at, cancelled_at all NULL) → PROCESSING (claimed_at set) → DONE (published_at set)`, with a side exit `PENDING → CANCELLED (cancelled_at set)` — reachable **only** from true PENDING (`claimed_at IS NULL`). A *stale* claim is **not** PENDING for cancellation purposes, even though the dispatcher's own poll/reclaim treats it as fair game to re-claim and complete — see below for why those two are different questions with different safe answers.

**Second use, same table (D4):** contract/pricing/billing also write `event_type = 'workflow.start_requested'` rows here, one per submit, in the same transaction as the local status commit. `payload` **must** include a freshly-generated `idempotency_key` at creation time — generated once, never regenerated on retry. Its "publish" target is a gRPC call (`WorkflowInternal.StartInstance(..., idempotency_key)`), not the broker — the relay retries the call (always with that same stored key) instead of a broker publish, and this event type never appears in §4's event catalog since nothing subscribes to it.

**Cancelling this dispatch, correctly** — a single check-and-fallback is not enough, and neither is treating a *stale* claim as safe to cancel directly. A timestamp lease has no fencing: "stale" only means the claim looks old from the outside, never that the worker holding it is actually dead — it may simply be paused (GC, VM stall, slow network) and resume later, exactly where it left off. If cancellation concluded "claimed_at is stale, so nothing will happen, cancel it" and set the document CANCELLED, that paused worker can still wake up afterwards and call `StartInstance` — nothing stops it, a timestamp isn't a lock. So the rule is stricter than "cancel unless claimed": **only a row with `claimed_at IS NULL` — truly never claimed by anyone — is ever cancelled directly.** Every claimed row, fresh *or* stale, is treated as potentially in flight, with no exception. Algorithm, retried with backoff until one branch resolves — **the document stays in its pre-cancel status throughout, never flipped to CANCELLED speculatively**:

1. `UPDATE outbox SET cancelled_at = now() WHERE id = ? AND claimed_at IS NULL AND cancelled_at IS NULL AND published_at IS NULL` — **no staleness clause**. 1 row affected ⇒ **done**: nobody has ever attempted dispatch, so no instance will ever be created. Set document CANCELLED, stop.
2. 0 rows ⇒ the row is claimed (fresh or stale — treated identically). Call `WorkflowInternal.CancelInstance`. `OK` ⇒ instance existed, now cancelled — set document CANCELLED, stop. `FAILED_PRECONDITION` ⇒ instance exists but a step was already actioned — cancel fails outright for the whole document (existing, unrelated behavior), stop. **`NOT_FOUND` ⇒ inconclusive, not terminal** (§5.1's one exception to "`NOT_FOUND` isn't retryable"): the instance may not exist *yet* for either of two reasons — a fresh claim's owner hasn't finished, or a stale claim's owner is paused, not dead. Don't distinguish them; **resolve the ambiguity instead of guessing**:
   - If the claim is still fresh (within the lease window): back off and retry from step 1 shortly — the owning worker is expected to finish very soon.
   - If the claim is genuinely stale: **recover the dispatch itself rather than assume it will never complete.** Re-claim the row exactly as the dispatcher's own reclaim would (`UPDATE ... SET claimed_at = now() WHERE claimed_at < now() - interval 'N seconds' AND published_at IS NULL AND cancelled_at IS NULL`); on success, call `WorkflowInternal.StartInstance` **itself**, using the row's own stored `idempotency_key` (below — **not** a fresh one); mark `published_at`; then retry from the top of step 2, which will now find the instance and call `CancelInstance` on it. If the original worker wakes up later and calls `StartInstance` too — with that same stored key, which is the only way this is safe (see below) — `workflow_instance.idempotency_key`'s permanent UNIQUE constraint hands it back the same, already-cancelled instance: a harmless no-op, never a second instance, regardless of what status the first one is in by then.

**Safety here depends on a stable, uniquely-stored `idempotency_key` — not on "any caller, any key," which was wrong.** The outbox row generates its `idempotency_key` exactly once, at creation, stored in `payload`; every retry of that row — the original dispatcher, a reclaiming worker, or this recovery path — must reuse that identical value, never generate a fresh one. `workflow_instance.idempotency_key uuid NOT NULL UNIQUE` (permanent, no status scoping — see db-workflow.md) is what makes this safe: `(document_type_code, document_id) WHERE status='IN_PROGRESS'` alone is *not* sufficient, because it stops applying the moment the instance leaves IN_PROGRESS — exactly what recovery's own `CancelInstance` call does. Without the permanent key-based constraint, a paused worker resuming *after* recovery had already cancelled the instance would sail past the now-inapplicable partial index and create a second, live one. The partial index keeps its own, separate job: rejecting a genuine concurrent double-submit (two *different* keys) while an instance is still active — the two constraints are not redundant, each closes a gap the other doesn't.

This always terminates and never reaches the state the fix set out to prevent: either a fresh claim's owner finishes on its own (→ `CancelInstance` finds it), or a stale claim gets forced to resolution by the canceller itself (→ guaranteed to exist, then guaranteed cancelled) before the document is ever marked CANCELLED. A fencing token at workflow-service (rejecting a stale worker's call outright) would also close this, but is unneeded machinery here — idempotency already makes the stale worker's eventual call harmless, so nothing needs to actively stop it.
