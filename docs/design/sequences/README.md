# PAS — Sequence diagrams (design phase 3)

Eight flows, generated by [`scripts/gen_seq_drawio.py`](../../../scripts/gen_seq_drawio.py) — edit the spec there and regenerate; the generator refuses malformed specs (unbalanced fragments, arrows to a nonexistent or same lifeline, participants that never exchange a message).

**Why flows and not one-diagram-per-service:** a sequence is inherently cross-service, so a "billing-service diagram" would either duplicate its neighbours or show billing talking to nothing. Instead each flow is a business scenario. Precisely: **every service that owns domain state appears in at least two flows**; esign-service and audit-service are each the subject of one dedicated flow (7 and 2) and appear implicitly wherever signing status or `audit.recorded` is produced; api-gateway is drawn once in flow 1 and implicit thereafter by the §8.2 convention; esign-mock-provider exists only in flow 7 by definition. That is what makes the request/response contracts checkable.

**Lifeline shapes** — draw.io's UML robustness stereotypes (Jacobson). Every diagram also carries this as a legend box at the bottom.

| Shape | Stereotype | Means | Used for |
|---|---|---|---|
| stick figure | actor | a human role outside the system | Sales officer, Approver, Accountant, Ops officer, System admin |
| circle with a bar on its left | boundary | the edge where the system meets the outside | api-gateway, MockSign provider |
| circle with an arrow on its rim | control | coordinating logic that isn't domain data | outbox relay, scheduler |
| circle on a line | entity | persistent data or a store | a Postgres schema, Redis, Kafka |
| plain rectangle | — | an ordinary participant | **the nine PAS services** |

Reserving plain rectangles for our own services is deliberate: an icon always means "not a PAS service". One caveat stated honestly — strict Jacobson *entity* means a persistent **domain** object, not infrastructure; using it for Redis/Kafka/schemas is a pragmatic convention.

**Arrows.** Solid filled = synchronous request (gRPC between services per D16, REST when the caller is a user or the external provider). Dashed open = response. Purple open = broker publish/delivery. Self-call = local work; where it says `tx:` everything listed commits atomically. Yellow notes carry the invariant that makes the step correct — they are the point of these diagrams, not decoration.

## 1 · Auth, authenticated request, permission resolution

Establishes the convention the other seven rely on: the gateway hop and the permission check happen on **every** user-facing call and are drawn once here.

The three-part sequence is login → authenticated request → logout, plus the `loop` at the top showing identity warming `perm:role:{code}` at startup and rewriting it hourly. The hourly sweep looks redundant until you see why it exists (§M1): a rewrite-on-change-only cache silently expires after one idle TTL with no trigger left to repopulate it.

The closing `opt` is the admin UC **Phân quyền**, and it is the half §M1 calls the common path: the same request that commits a `role_permission` change overwrites `perm:role:{code}`, so a revoke lands in seconds rather than at the victim's next login. Drawn deliberately *after* the COMMIT and *outside* the transaction — Redis cannot join a Postgres commit, and a failed cache write must not roll back an authorization change already reported as succeeded. That is what makes the hourly loop at the top a bound rather than a duplicate. The contrast worth reading twice: editing a **role's permissions** propagates through Redis; editing a **user's roles** writes only `user_role` and lands at next login, because `roles[]` is a JWT claim.

**Contracts used:** REST `POST /auth/login`, `POST /auth/logout`, `PUT /roles/{role_code}/permissions`; Redis `blacklist:{jti}`, `perm:role:{code}`. **Invariants:** JWT carries `roles[]` only; layer 1 (gateway: signature, exp, blacklist, coarse role) and layer 2 (service: permission from the cache) are distinct; Redis down ⇒ `PERMISSION_DENIED`.

## 2 · Outbox relay, centralized audit, notification fan-out

The mechanics diagram. Flows 3–8 reference it rather than redrawing the broker.

Four things it pins down: (a) the single business transaction writes status + `status_history` + both `outbox` rows — this is what makes 4.10 unconditional and 5.5's lost-event row answered; (b) the relay's claim `UPDATE` must repeat the poll's staleness clause exactly, or a crashed worker's row satisfies the `SELECT` forever and the claim never matches; (c) audit dedups on `id = event_id` with `ON CONFLICT DO NOTHING`, so it needs no `processed_event`; (d) the History tab reads **two** sources with different consistency — local `status_history` (synchronous) and `AuditInternal.ListRecords` (eventual). A business rule may only read the former (D17). Since the broker switch it also pins **(e)** Kafka's own semantics in one place: the send carries `key = aggregate_id` — always the document id, so one partition per document — plus `event_type` / `document_type` headers for pre-deserialization filtering; `published_at` is stamped only after the `acks=all` ack; fan-out is a consumer group per service rather than a binding; and a record that can never succeed goes to `pas.events.DLT`, because unlike a requeue a stuck record blocks its whole partition. The note also states the limit of all this: Kafka orders what was *sent*, so commit order survives only under §M2's relay constraint and no consumer may depend on it (D2, §9¹).

The final fragment is the admin UC **Tra cứu audit log**, put here rather than in a diagram of its own so the two read paths sit side by side: `AuditInternal.ListRecords` is gRPC, keyed on one `(entity_type, entity_id)`, and fills an owning service's History tab; `GET /audit-records` is user traffic through the gateway, filtered on actor / service / action / date with pagination, gated by `audit:view_all`. Neither substitutes for the other, which is why the second one had to exist. Both are read-only against a table granting `INSERT + SELECT` only.

**Contracts used:** `AuditInternal.ListRecords`, `IdentityInternal.ListUsersByRole`, Kafka `pas.events` / `pas.audit`, REST `GET /notifications`, `PATCH /notifications/{id}/read`, `GET /audit-records`.

## 3 · Contract create → submit → approval → Active

The flagship, and the one that had to be re-derived against D4's rewritten ordering.

Submit is **two phases**: one local transaction (`DRAFT → SUBMITTED` + history + `workflow.start_requested` outbox row carrying a freshly-generated `idempotency_key`), then a relay that retries `WorkflowInternal.StartInstance` until it succeeds. The user gets `200 {status: SUBMITTED, workflow: initialization pending}` immediately. The two constraints on `workflow_instance` do different jobs and both appear: the permanent `idempotency_key UNIQUE` makes retrying *this dispatch* safe at any status, the partial index on `WHERE status='IN_PROGRESS'` rejects a *concurrent differently-keyed* double-submit.

The approval action shows APR-01/02 collapsing into one predicate — `caller ∈ step_assignee AND step.status='ACTIVE'` — and D5's guarded `UPDATE … WHERE version = ? AND status = 'ACTIVE'`, where 0 rows means `ABORTED`. The `alt` covers all three outcomes, each of them **order-tolerant** per §9¹: the completion guard admits `SUBMITTED` as well as `UNDER_REVIEW`, so a `workflow.completed` that overtakes a delayed `workflow.instance_started` applies the skipped `SUBMITTED → UNDER_REVIEW` edge first and then the outcome, one `status_history` row per edge, in one transaction — Kafka orders sends, not commits (D2), so the pair has to work in either order. The scheduler `loop` at the bottom does CTR-05 and D9, and carries the D14e note that contract status never reacts to e-sign.

Between the two sits the read 4.7 asks for by name — **Theo dõi tiến độ & người xử lý**: `GET /contracts/{id}/progress` behind `WorkflowInternal.GetInstanceByDocument`, returning the current step's assignees, the completed steps with their `actioned_by`/`comment`, and the PENDING tail. It reads the *snapshots* taken at instance creation, so the panel shows the chain that actually ran rather than today's definition (seq-08), and it is synchronous domain data — the third read path in the system, distinct from the owner's local `status_history` (D17) and from audit's eventual trail (seq-02). Two contract details the `alt` makes explicit. **Which instance:** revise and resubmit each mint a new `idempotency_key`, so a document accumulates terminal instances — the method returns the `IN_PROGRESS` one when it exists (the partial unique makes that at most one) and otherwise the latest by `created_at`. **The other branch is composition, not retry:** a `NOT_FOUND`, or a terminal instance while the document is still `SUBMITTED`, is D4's dispatch window; contract-service renders `INITIALIZATION_PENDING` from that plus its own status rather than calling again, so §5.1's single `NOT_FOUND` exception (`CancelInstance`) stays single. Ignoring the stale terminal instance is what stops a resubmitted document showing its previous rejected chain.

**Contracts used:** `WorkflowInternal.ValidateStartable` (new — see deltas), `WorkflowInternal.StartInstance`, `WorkflowInternal.GetInstanceByDocument`, `IdentityInternal.ListUsersByRole`, REST `POST /contracts`, `…/attachments`, `…/submit`, `GET /contracts/{id}/progress`, `POST /workflow-steps/{id}/actions`; events `workflow.instance_started`, `workflow.step_assigned`, `workflow.completed`, `document.expiring`, `audit.recorded`.

*Addendum uses this diagram unchanged* — its own 2-step chain, its own instance, and on reaching ACTIVE it applies `new_valid_to` / `payment_term_override` to the parent contract in the same transaction (registry §9²).

## 4 · Price list version

Exists mainly to draw one ordering that is easy to get wrong and impossible to notice later: **truncate the predecessor before approving the successor.** Setting the successor to `APPROVED` first trips the `EXCLUDE USING gist` constraint (PRC-03) and PRC-04's supersede flow becomes unreachable — the bug the pricing critic caught. Both `UPDATE`s and the history row are one transaction (§9³).

Also drawn: `addendum_id` provenance (D8 — manual, by Sales, post-approval), the scheduler's `EFFECTIVE`/`SUPERSEDED`/`EXPIRED` flips, and the **historical** resolution `GetEffectivePriceList` performs — precedence `CONTRACT > CUSTOMER+GROUP > CUSTOMER`, `date = period_end`, `SUPERSEDED`/`EXPIRED` versions included when their range contains the date. Without that last property a June statement rebuilt in July would silently reprice.

## 5 · Volume recording & period lock

Short, and load-bearing for PAY-02. The period's `LOCKED` state is the *only* confirmation signal; volume rows deliberately have no status of their own.

The `alt` is the interesting half: a post-lock edit is `403` for a normal Ops officer and permitted for a holder of `volume:edit_locked` — a permission in **no role bundle by default** — with a mandatory `audit.recorded` write. 4.5's escape hatch is defensible only because every use is traced. Note also two different durability decisions in one handler: `operations.period_locked` publishes directly (informational, self-heals by being re-derivable), while `audit.recorded` beside it is always outboxed.

## 6 · Payment statement

Billing is the only service that reads three others in one operation, in a fixed order because each check gates the next: contract (ACTIVE + period within validity, PAY-01) → volumes (period `LOCKED`, PAY-02) → effective price version at `period_end`. Then the guard that had no defined source until now: **every volume's `service_code` must be priced in the resolved version**, else `422` — this is PAY-01's "bảng giá phù hợp" failing concretely rather than producing a statement with silent gaps.

The write transaction is where PAY-03 lives: `unit_price`, `service_name`, `unit`, `vat_rate`, `payment_term`, `contract_no`, `customer_name`, `price_list_no + version_no` are all snapshots. The uuids remain for navigation only. A controlled edit flips `source = 'MANUAL'` and drops the status back to `DRAFT` (D14f) so the reconciliation panel can't show a stale tick.

## 7 · E-signature

Manual send by the document owner (D10), never event-triggered on approval. Billing commits `APPROVED → SIGNING` locally with an `esign.session_requested` outbox row and lets the relay retry `EsignInternal.CreateSigningSession` — the same pattern as D4, chosen so there is one dispatch mechanism in the system rather than two, and so no crash can leave a session sending for a statement still `APPROVED`.

The async half: `POST /callbacks/esign` is D16's single REST exception (the caller is outside the boundary and gets a URL, not a `.proto`). Every callback is logged first — `session_id` is nullable so an unknown `provider_ref` is still recorded — then a version-guarded `UPDATE` applies it, making duplicate and late callbacks no-ops. Send failures park in `PENDING_SEND` with `attempts`/`last_error` and terminate at `FAILED` after 3 tries rather than retrying forever. `FAILED`/`CANCELLED` sends the statement to `REVISION` (PAY-07); `SIGNED` then `publish` computes `due_date` and reaches `ISSUED`.

## 8 · Workflow configuration — the admin side of 4.7

The flow that proves the requirement's sharpest technical clause: *"Quy trình phê duyệt không được hard-code theo if/else đơn giản."* Everything else treats the chain as given; this one shows it being changed at runtime, by a human, with no deploy.

Three things it pins down. **(a) There is no edit-in-place path.** An active version is read-only, so every change is `POST /workflow-definitions` (copy → new `version_no`, `is_active = false`) → `PUT …/steps` → `POST …/activate`. Figma's drag-reorder is a `step_order` rewrite on the draft. **(b) The activation swap has an ordering hazard of exactly seq-04's shape, plus a guard requirement the ordering alone doesn't cover** — the partial unique `(document_type_id) WHERE is_active` admits one active version per document type, so the old version must be deactivated *before* the new one is activated, and both must be in one transaction. Ordering is necessary and not sufficient: a missing target or an unchecked zero-row activation can otherwise let an unpaired deactivate commit, leaving the document type with **no** active definition — every subsequent submit failing `ValidateStartable`, with nothing raised at the moment of damage. So the transaction locks the target `FOR UPDATE`, asserts it exists, and uses that row's `document_type_id` as the swap scope. An already-active target is an idempotent `200` with no writes or duplicate audit record; an inactive target must activate exactly 1 row or `ROLLBACK`. The deactivate may legitimately report 0 (first activation for a freshly seeded document type; the partial unique already bounds it to ≤ 1) — it is the activate's count that carries the invariant. Concurrent activations serialize on the incumbent row and the loser aborts on the partial unique. **(c) Running approvals do not move.** `workflow_instance.definition_id` pins the version and `step_assignee` was snapshotted at instance creation, so nothing on the action path reads `workflow_step_definition` at all — the v3 approval finishes as v3 while the next submit starts on v4. That is the reason for versioning rather than editing: a chain mutating mid-flight would change "các bước còn lại" under a live document, could strand an `ACTIVE` step whose role left the chain, and would move the step numbers APR-02 depends on.

One deliberate non-check: activation does **not** verify that each step's role has an `ACTIVE` holder. A chain is legitimately configured before the people exist, and `ValidateStartable` already rejects the submit and names the unfillable role (delta 1). Two gates for one fact would only let the config screen and the submit screen disagree.

**Contracts used:** REST `GET|POST /workflow-definitions`, `PUT /workflow-definitions/{id}/steps`, `POST /workflow-definitions/{id}/activate`, `POST /workflow-steps/{id}/actions`; `WorkflowInternal.StartInstance`; event `audit.recorded`.

## Registry deltas introduced by this phase

Drafted here per the plan's protocol; applied to [00-registry.md](../00-registry.md) in the same commit, with a change-log entry.

0. **Response shapes made explicit → §5.** Drawing the flows exposed six fields consumed with no source: `service_group` (needed as the pricing scope key) and `currency` on `GetContract`; `service_name` + `unit` on `GetEffectivePriceList` lines (pricing owns the catalog, so it is the authority for the PAY-03 line snapshot — not a snapshot-of-operations'-snapshot); `period_start`/`period_end` on `ListVolumes` (the owner's values, since billing snapshots them rather than re-deriving from the `period_code` string). Also new: **`PricingInternal.GetServiceItem(code)`** and an `operations → contract` `GetContract` call, so a volume entry validates its `service_code` and captures its D7 snapshots at entry time instead of letting a typo surface weeks later as billing's misleading "no suitable price list".
1. **`WorkflowInternal.ValidateStartable(document_type)` → §5.** Read-only. Returns `OK` when every step of the active definition resolves to ≥ 1 `ACTIVE` assignee, `FAILED_PRECONDITION` naming the unfillable role otherwise. **Why it had to exist:** `db-workflow.md` promised that a zero-assignee step "fails the submit — nothing strands", but D4's ordering commits `SUBMITTED` *before* dispatching, so that promise was unimplementable — the dispatcher would just retry forever against a document already reported as submitted. A read-only pre-check restores the immediate error without reintroducing the orphan D4 forbids (a *mutating* call before the local commit is exactly what D4 rejects). It cannot close the race where a user is disabled between check and dispatch; that case falls through to D4's retry and the "initialization pending" state, which is visible rather than silent.
2. **`esign.session_requested` → §6, third-use list.** Another `outbox` `event_type` whose publish target is a gRPC call (`EsignInternal.CreateSigningSession`), exactly like `workflow.start_requested`. Not in §4's catalog — nothing subscribes. Alternative considered and rejected: calling esign synchronously and committing `SIGNING` after, which on a crash between the two leaves a session that will send to the provider and later deliver a callback for a document still `APPROVED` — a status §9 has no transition from. Written by **both** billing (in the same transaction as `APPROVED → SIGNING`) and contract-service (with *no* status change, D14e — the outbox is still right because APR-07 wants the send action to survive esign being down).
3. **`signing_session.idempotency_key uuid NOT NULL UNIQUE` → §5/§6 + db-esign.** Delta 2's dispatch is only idempotent with it. The existing partial index is status-scoped (`WHERE status IN ('PENDING_SEND','SIGNING')`), so once a session terminates it stops applying — a relay that crashed before stamping `published_at` would re-dispatch, create a **second** session, send to the provider again and deliver a second callback for an already-signed document: exactly the orphan delta 2 exists to prevent. Same two-constraint split as `workflow_instance` (D4), and the reason the earlier "idempotent via the partial unique" claim was wrong.
4. **`GetSigningPayload` guard widened → §5.** D10 documented "fetch the payload of an **Approved** document", but delta 2 moved billing's flip ahead of the call, so a statement is never `APPROVED` when esign fetches. Guard is now `APPROVED` for contract/addendum and `{APPROVED, SIGNING}` for statements; an `APPROVED`-only guard would have deadlocked every statement send on an unbounded retry.
5. **`esign:cancel` permission + session cancel path → §7/§9.** §9 already made `CANCELLED` a *user* transition, but no flow drew it and no permission existed, so 4.8's "hủy ký" had no mechanism. The callback branch is now labelled `[result FAILED]` only — a provider never *reports* a cancellation.
6. **Callback URL carries `session_no`, and the callback guard accepts `PENDING_SEND`** → db-esign. Correlating on `provider_ref` alone is impossible before the 202-handling transaction commits, so a provider calling back faster than that would be logged as unknown and dropped — leaving the session waiting forever for a callback that already happened (§9 gives `SIGNING` no timeout exit).
7. **`GET /audit-records` (user-facing REST, `audit:view_all`) → db-audit.** db-audit.md promised cross-entity search — *"what did user X do last week", "every reject in Q3"* — and carries the indexes for it (`(actor_id, occurred_at DESC)`, `(source_service, occurred_at DESC)`, `(action)`), but no endpoint ever exposed them: the only defined read was `AuditInternal.ListRecords`, which is gRPC, per-entity, and serves an owning service's History tab. So the admin UC *Tra cứu audit log* had indexes, a permission and a Figma screen with nothing to call. Filters `entity_type / entity_no / actor_id / source_service / action / from / to`, paged, `ORDER BY occurred_at DESC`. REST because it is user traffic (D16), and read-only because the schema grants `INSERT + SELECT` only.
8. **Admin workflow-definition endpoints → db-workflow.** `GET|POST /workflow-definitions`, `PUT /workflow-definitions/{id}/steps`, `POST /workflow-definitions/{id}/activate`, all gated by `workflow:configure`. The *semantics* were already fixed (version + `is_active` partial unique, "admin edit = insert version + flip"); what was missing is that no artifact said how an admin performs it, which left 4.7's headline requirement with no drawn mechanism. Deactivate-then-activate in one transaction is stated here for the first time — it follows from the existing partial unique, and getting it backwards makes the swap impossible rather than merely wrong. The guards around it are new too, and load-bearing: `FOR UPDATE` plus existence validation on the target, idempotent success when it is already active, its own `document_type_id` as the swap scope, and `activated = 1 else ROLLBACK` for an inactive target. Without them an unpaired deactivate can commit and strand the document type with no active chain. Recorded in db-workflow.md.
9. **`PUT /roles/{role_code}/permissions` (`user:manage`) → db-identity.** §M1 specified the *effect* of a `role_permission` change in detail (same-request Redis overwrite, best-effort, non-transactional, bounded by the hourly sweep) without naming the request that causes it. Now drawn in flow 1, including the two properties that are easy to get wrong when implementing: the cache write is after the COMMIT and outside the transaction, and a `user_role` change writes no cache at all.

## Known deviation from the previous phase

The plan's Phase 3 originally specified **mermaid**; these are draw.io, matching the ER diagrams and the shape vocabulary the reviewer supplied. Plan §8.2 was updated accordingly. Consequence accepted: diagrams are generated, not hand-edited, so a change means editing the spec — which is also what keeps the 7 flows using identical names for the same call.
