One PostgreSQL instance in dev, **database per service** (`pas_identity`, `pas_contract`, …), each owned by its own least-privilege login role, **no cross-service queries** (D12).

**Dual protocol stack (D16).** Every service exposes two surfaces:
- **REST/JSON on its 80xx port** — user-facing endpoints, reached only through the edge (Traefik) under `/api/v1/{resource}` (the edge strips `/api/v1` before forwarding, so a service serves `/auth`, `/users`, … itself); documented with OpenAPI/Swagger (req §6). Also the transport for inbound webhooks.
- **gRPC on its 505x port** — service-to-service only, never routed by the edge, never reachable from outside the compose/cluster network.

The old `/internal/**` REST path convention is retired: internal calls are gRPC methods, so there is no internal HTTP route left to accidentally expose.

## 4. Event catalog

Envelope (all events): `{event_id: uuid, event_type, occurred_at, actor_id, actor_name, document_type, document_id, payload{}}` — that is the *logical* event. **On the wire the record value is `payload{}` alone**, and the envelope fields a consumer actually needs travel as Kafka headers: `event_id` (the dedup key), `event_type` and `document_type`. This is what `OutboxRelay#kafkaRecord` has always published — the value is the outbox row's `payload` column verbatim — and the three direct publishers (D9) match it, so there is exactly one parse path in every consumer and no event is special-cased. `occurred_at` / `actor_id` / `actor_name` are not on the wire at all: the audit trail takes them from the `audit.recorded` payload, which carries its own copies, and no other consumer reads them. Broker: **Kafka** (D2) — topic `pas.events` for every event below except `audit.recorded`, which has its own topic `pas.audit` (highest volume, single consumer). Message **key = `aggregate_id`**, which for every event in this table is the **document** id — never the workflow instance id — so all events about one document share a partition. Kafka preserves per-partition **send** order; that equals commit order only under §M2's relay constraint (poll `ORDER BY created_at`, one publisher per service), so it is a strong default, not an invariant a consumer may rely on — see footnote ¹ for the one transition chain that had to be made order-tolerant. The three events published **without** an outbox row (D9) have no `aggregate_id` and set the key explicitly, or they would round-robin across partitions: `document.expiring` and `workflow.step_overdue` key on the document id, `operations.period_locked` on `period_code`. `event_type` **and** `document_type` are mirrored into Kafka **headers** so a consumer can skip a record before deserializing the payload — there is no broker-side routing, and the owner-service groups discriminate on `document_type`, not on `event_type`. The Consumers column below is therefore a list of **consumer groups** (one per consuming service), not of bindings; a record that can never be processed goes to `<topic>.DLT` so the offset can advance.

| event_type | Producer | Outbox? | Consumers | Payload extras |
|---|---|---|---|---|
| `workflow.instance_started` | workflow | yes (D6) | owner service (flips SUBMITTED → UNDER_REVIEW, §9¹) | `instance_id, document_no, priority` |
| `workflow.step_assigned` | workflow | yes | notification | `instance_id, step_no, step_name, assignee_ids[], document_no, customer_name` |
| `workflow.step_actioned` | workflow | yes | notification | `instance_id, step_no, action, comment, document_no, requested_by` (uuid), `requested_by_name` |
| `workflow.completed` | workflow | yes | owner service (status flip, D3), notification | `instance_id, outcome, document_no, requested_by` (uuid), `requested_by_name` |
| `workflow.step_overdue` | workflow (scheduler vs `sla_hours`) | no — self-heals next run (D9 logic) | notification | `instance_id, step_no, step_name, assignee_ids[], waiting_hours, sla_hours, document_no` |
| `esign.session_completed` | esign | yes | billing (status flip, D3 — statements keep their native Signing/Signed transitions), notification | `session_id, result: SIGNED\|FAILED\|CANCELLED, error?, document_no, requested_by, signer_name` |
| `document.expiring` | contract, pricing (schedulers) | no — self-heals next run (D9) | notification | `document_no, expires_on, days_left, owner_user_id` |
| `operations.period_locked` | operations | no — informational only | notification | `period_code, locked_by_name, recipient_role: 'ACCOUNTANT'` |
| `audit.recorded` | identity, contract, pricing, operations, billing, workflow, esign | **yes — always** (D15) | audit | full audit row: `source_service, entity_type, entity_id, entity_no, action, actor_id, actor_name, actor_department, before_status, after_status, changes, note, ip_address, occurred_at` |

Consumers are idempotent via a `processed_event` table (D6). **Recipient resolution:** events carry recipient user ids where the producer knows them (`assignee_ids`, `requested_by`, `owner_user_id`); role-addressed events carry `recipient_role`, which notification-service resolves via identity (§5).

## 5. Sync API dependency matrix

All service-to-service calls are **gRPC** (D16); frontend→gateway→service REST is omitted. Signatures indicative; finalized in the `.proto` files.

| Caller → Callee | gRPC method | Purpose |
|---|---|---|
| billing, operations → contract | `ContractInternal.GetContract(id)` | returns `status, valid_from, valid_to, service_group, vat_rate, payment_term, customer_id, customer_name, contract_no, currency` — the **effective** values (addendum effects already applied, §9²). `service_group` is the pricing lookup's scope key; billing snapshots the rest (PAY-01/03). Operations uses it to validate the contract and snapshot `customer_name` |
| operations → pricing | `PricingInternal.GetServiceItem(code)` | returns `name, unit, is_active`; `NOT_FOUND` ⇒ reject the volume entry. Validates **and** supplies the D7 snapshot at entry time, so a bad `service_code` fails immediately instead of surfacing weeks later as billing's "no suitable price list" |
| billing → pricing | `PricingInternal.GetEffectivePriceList(contract_id, customer_id, service_group, date)` | effective version + lines for snapshot (PAY-01/03). Resolution precedence: CONTRACT-scoped > CUSTOMER+GROUP > CUSTOMER. `date` = the statement's `period_end`; lookup is **historical** — includes SUPERSEDED/EXPIRED versions whose validity contains `date` |
| billing → operations | `OperationsInternal.ListVolumes(contract_id, period_code)` | returns `period_state, period_start, period_end, volumes[{record_no, service_code, unit, quantity}]` — the period bounds come from the owner's row, not re-derived from the code string, because billing snapshots them (PAY-02/03) |
| workflow → identity | `IdentityInternal.ListUsersByRole(role_code)` | resolve step role → assignees for every step, in one pass at instance creation (APR-01); returns `status='ACTIVE'` users only |
| esign → contract | `ContractInternal.GetSigningPayload(document_type, id)` (contract + addendum) | document render for provider (D10). Guard: status ∈ {`APPROVED`, `ACTIVE`} — sending still starts from `APPROVED` only, but D14d activates the document on its effective date regardless of a session in flight, so an `APPROVED`-only guard would refuse the payload for exactly the documents legitimately sent (same deadlock as billing's, reached from the other side) |
| esign → billing | `BillingInternal.GetSigningPayload(id)` | document render for provider (D10). Guard: status ∈ {`APPROVED`, `SIGNING`} — billing flips to `SIGNING` **before** the dispatch (§6 third use), so an `APPROVED`-only guard would deadlock every send on an unbounded retry |
| owner services → esign | `EsignInternal.CreateSigningSession(document_type, document_id, document_no, signer_name, signer_email, idempotency_key)` | manual send-for-signing (D10). A *different* key hitting the partial index = a genuine concurrent double-send ⇒ `FAILED_PRECONDITION`, not retryable |
| owner services → workflow | `WorkflowInternal.ValidateStartable(document_type)` | **read-only pre-submit check**: `OK` when every step of the active definition resolves to ≥1 `ACTIVE` assignee, else `FAILED_PRECONDITION` naming the unfillable role. Called *before* the local `DRAFT → SUBMITTED` commit so a misconfigured chain is rejected immediately; it must stay a read, since a mutating call before that commit is the orphan D4 forbids. Residual race (a user disabled between check and dispatch) falls through to D4's retry + the "initialization pending" state |
| owner services → workflow | `WorkflowInternal.StartInstance(document_type, document_id, …, idempotency_key)` | start approval on submit (idempotent, D4) |
| owner services → workflow | `WorkflowInternal.GetInstanceByDocument(document_type, document_id)` | progress display ("ai đang giữ hồ sơ", 4.7) — drawn in seq-03. **Which instance:** a document can accumulate several *terminal* instances, since CTR-04's revise and `REVISION_REQUESTED → DRAFT → submit` each generate a new `idempotency_key` and therefore a new instance. Selection is therefore defined, not implied: **return the `IN_PROGRESS` instance if one exists** — the partial unique `(document_type_code, document_id) WHERE status='IN_PROGRESS'` guarantees at most one, so this is total, not a tie-break — **otherwise the latest terminal instance by `created_at DESC`**; `NOT_FOUND` only when the document has never had one. **Response:** `instance_id, status, definition_version_no, requested_by_name, started_at, priority`, `current_step? {step_no, name, assignee_names[], activated_at, sla_hours, is_overdue}`, `steps[{step_no, name, approver_role, status, assignee_names[], action? {actor_name, actioned_at, comment?}}]` — 4.7's three demands in one response: current holder, completed steps, remaining steps. **Nullability is part of the contract:** `current_step?` is absent for a terminal instance (APPROVED / REJECTED / REVISION_REQUESTED / CANCELLED — no holder exists, and an empty object would read as one); `action?` is absent on ACTIVE and PENDING steps, present exactly where a `workflow_action` row exists; `comment?` inside it is optional too — APR-03 makes a reason mandatory only for REJECT and REQUEST_REVISION, so an APPROVE may carry none. `is_overdue = status = 'ACTIVE' AND now() > activated_at + sla_hours`, derived on read from the same columns the SLA sweep compares, so the panel and `workflow.step_overdue` cannot disagree. All values come from workflow's own `workflow_step_instance` / `step_assignee` snapshots + `workflow_action`, so the panel shows the chain that actually ran, not today's definition. **Synchronous domain data, never the audit trail** (D15/D17). **Owner-side composition, not retry** (§5.1 unchanged): the caller reads the result together with its own status — when the local status is `SUBMITTED` and the response is **not** an `IN_PROGRESS` instance — whether that is `NOT_FOUND` or a terminal instance from the previous submission — the owner renders `INITIALIZATION_PENDING` and discards the returned instance; without that discard a resubmitted document displays its previous rejected chain for the whole dispatch window |
| owner services → workflow | `WorkflowInternal.CancelInstance(document_type, document_id, idempotency_key)` | cancel in-flight approval when the document is cancelled; `FAILED_PRECONDITION` if a step was already actioned (retried on `UNAVAILABLE`, APR-07 spirit). **Not `instance_id`** — during the §6 cancel/dispatch handoff the caller may not know it yet (that's the whole point of the ambiguity being resolved); it always has `document_type`/`document_id` (the document being cancelled) and `idempotency_key` (read straight off its own outbox row), so workflow-service looks the instance up by `idempotency_key` (unique, D4) and cross-checks it against `document_type`/`document_id`. `NOT_FOUND` retried per §5.1's one exception. |
| notification → identity | `IdentityInternal.ListUsersByRole(role_code)` | resolve `recipient_role`-addressed events to users (§4); returns `status='ACTIVE'` users only |
| owner services → audit | `AuditInternal.ListRecords(entity_type, entity_id, page)` | the **non-status** half of the History tab (field edits, actions without a status change). The status timeline reads local `status_history` (D17) — no call |

### 5.1 gRPC conventions (D16)

- **Package / naming:** `pas.<service>.v1`; one internal service per callee, named `<Service>Internal`. Methods are verbs (`GetContract`, `ListVolumes`, `StartInstance`); request/response messages are `<Method>Request` / `<Method>Response` — never bare domain messages, so fields can be added without breaking callers.
- **Proto ownership:** `.proto` files live with the **callee** and are published to a shared `proto/` module that callers depend on. Contract-first: the proto changes before either side does.
- **Status-code mapping** (replaces the previous HTTP codes):
  `NOT_FOUND` (unknown id) · `INVALID_ARGUMENT` (validation) · `FAILED_PRECONDITION` (state-machine violation, e.g. cancel after a step was actioned — was 409) · `ABORTED` (optimistic-lock loss, D5 — was 409) · `PERMISSION_DENIED` (D11 layer 2) · `UNAVAILABLE` (callee down — the **only** retryable status in general). **One deliberate, narrow exception:** `CancelInstance` returning `NOT_FOUND` during the outbox cancel/dispatch handoff (§6, §9 footnote ¹) — there, `NOT_FOUND` doesn't mean "permanently absent," it means "not created *yet*, creation may still be in flight," so it is retried like `UNAVAILABLE` in that one caller. **Retryability and permanence are separate questions** — the rule is about the first, and stating it as "everything else is permanently absent" was wrong, because absence can be transient without being retryable:
  - `NOT_FOUND` is **non-retryable by default**. A caller that receives it must not call again.
  - **`CancelInstance` is the only retry exception** (above): there, absence means "not created *yet*", and retrying is how the ambiguity resolves.
  - **`GetInstanceByDocument`'s absence is composed, not retried.** It too can be transient (a document `SUBMITTED` whose D4 dispatch hasn't landed), but the caller renders it — `NOT_FOUND` plus its own status becomes `INITIALIZATION_PENDING` — rather than calling again. A displayed absence needs no change to the retry rule, and widening `NOT_FOUND` for every caller would buy nothing that owner-side composition doesn't already give.
- **Idempotency (D4):** `idempotency_key` is an explicit field on mutating request messages, not a header. Retrying `StartInstance` with the same key returns the existing instance **regardless of that instance's current status** — backed by `workflow_instance.idempotency_key uuid NOT NULL UNIQUE` (permanent, not status-scoped; db-workflow.md), not by the separate partial `(document_type_code, document_id) WHERE status='IN_PROGRESS'` index, which only rejects *concurrent, differently-keyed* submissions while active (§6 explains why both are needed).
- **Deadlines:** every call sets one (default 2s reads / 5s writes). A caller without a deadline is a bug — an unbounded internal call can stall a user request behind it.
- **Failure = the document is unaffected.** Callers must not leave partial state when a callee is `UNAVAILABLE`; retry with backoff, or fail the whole transaction (APR-07).
- **gRPC is never exposed publicly.** The edge routes REST only; the `505x` ports are unreachable from outside the network. The public surface stays REST/JSON, which is what OpenAPI (§6) documents.

## 6. Common column & table conventions

- `id UUID PK DEFAULT gen_random_uuid()`; `created_at timestamptz NOT NULL DEFAULT now()`; `created_by uuid` (+ `created_by_name text` where displayed); `updated_at`, `updated_by`; `version int NOT NULL DEFAULT 0` **only** where a race is real (D5 targets).
- Status columns: `text` + `CHECK` against §3 enums.
- Cross-service references: opaque `uuid` (+ business-number/name snapshot columns where the UI or history needs them, D7). Never a real FK across schemas. **Two business-key exceptions** (stable, human-legible codes): `pricing.service_item.code` (referenced as `service_code` by operations/billing) and `operations.operation_period.period_code` (referenced by billing).
- **Two-token auth, validated at the edge (D11).** Login returns a short **access token** (**RS256** JWT, **15 min** — identity signs with its private key, the edge validates with the public key) and a long **refresh token** (opaque 256-bit, **14 days**, SHA-256-hashed and stored in `pas_identity.refresh_token`). `POST /auth/refresh` rotates both — new access + new refresh, old refresh revoked; presenting an already-revoked refresh token is a theft signal that revokes the whole token **family**. Logout and user-disable revoke the family. There is **no JWT blacklist** — access tokens are un-revocable by design and just expire; revocation lives on the refresh side (≤15-min lag). `/api/v1/auth/login`, `/api/v1/auth/refresh`, `/api/v1/auth/logout` are the only unauthenticated endpoints.
- **JWT (access-token) claims** (issued by identity, validated **at the edge**, D11): `sub` (user id), `username`, `full_name`, `department`, `roles[]` (§7 codes), `jti` (token id, for correlation/logging), `exp`. The **edge validates the signature once** and **injects the identity as trusted headers** — `X-User-Id`, `X-Username`, `X-Full-Name`, `X-Department`, `X-Roles` — stripping any client-supplied copies. **Services read those headers** (no JWT, no crypto) and never re-validate. This is gateway-centric auth, sound only because the internal network is sealed (services publish no host ports; the edge is the sole ingress).
  **Permissions are not a header** — services resolve `roles[] → permissions[]` from a Redis-cached map: one key per role, `perm:role:{role_code}` → JSON array of permission codes, **written only by identity-service**. A `permissions[]` claim would go stale until re-login; a per-request identity call would sit on the hot path. Refresh: every role warmed at identity startup, rewritten on a fixed **1h** schedule regardless of change, and rewritten immediately (best-effort) in the same admin request that commits a `role_permission` change; **TTL 6h** is last-resort self-heal, not the primary mechanism. `user_role` changes need no Redis write (the JWT already carries `roles[]`). **Redis unavailable ⇒ `PERMISSION_DENIED`, fail closed** — never a permissive default. Net guarantee: **bounded eventual revocation**, not hard immediacy. Full rationale and failure analysis: [mechanics.md §M1](mechanics.md#m1--permission-cache-d11).
- **status_history** (D17) — in the four schemas owning a state machine (`contract`, `pricing`, `billing`, `esign`). **Append-only, INSERT+SELECT only**, one row written in the **same transaction** as every status column change, so the column is a cache of the newest row and the two are cross-checkable:
  `id uuid PK, <owner ref>, from_status, to_status, trigger_kind, trigger_ref uuid NULL, actor_id uuid NULL, actor_name, note, occurred_at timestamptz`.
  Owner ref: `entity_type`+`entity_id` in `contract` (polymorphic CONTRACT|ADDENDUM, as `attachment`); a real FK elsewhere. `trigger_kind ∈ U|W|E|S` (§9); `trigger_ref` = workflow instance id (W), event id (E), null otherwise.
  **Domain data, not audit** — the only history a business rule may read, and the source of the detail-screen status timeline.
- **Audit is centralized (D15).** No per-service `audit_log`. Auditable actions write an `audit.recorded` row to the service's `outbox` in the same transaction; audit-service is the sole store, and serves the non-status part of the History tab (eventually consistent). Payload (per Figma Audit Log screen):
  `source_service, entity_type, entity_id uuid, entity_no, action (snake_case verb: submit_for_approval, approve_step, …), actor_id uuid NULL (NULL = system), actor_name, actor_department, before_status, after_status, changes jsonb, note, ip_address, occurred_at`.
- **outbox** (every service that emits any event — all but notification):
  `id uuid PK (= envelope event_id), event_type, aggregate_type, aggregate_id uuid, payload jsonb, created_at, claimed_at timestamptz NULL, published_at timestamptz NULL, cancelled_at timestamptz NULL, retry_count int DEFAULT 0`.
  `aggregate_type`/`aggregate_id` = routing/ordering key (Debezium convention): `aggregate_id` **is** the Kafka message key and is always the *document* id, so the same document ⇒ one partition; commit order additionally requires §M2's relay constraint (D2). **One `outbox` per service, never one per event type** — the event name is the `event_type` column. Relay: claim a pending row, act, stamp `published_at` on success — for a broker publish, only after the `acks=all` ack (or clear `claimed_at` + increment `retry_count`); a claim left stale by a crashed worker is reclaimed after a lease window. **At-least-once** — consumers dedup via `processed_event` or a natural PK. Lifecycle: `PENDING (claimed_at, published_at, cancelled_at all NULL) → PROCESSING (claimed_at set) → DONE (published_at set)`, with a side exit `PENDING → CANCELLED (cancelled_at set)` reachable **only** from true PENDING (`claimed_at IS NULL`) — a *stale* claim is never treated as cancellable.
  **Third use, same pattern (D10):** **billing *and* contract-service** write `event_type = 'esign.session_requested'` on send-for-signature, with a once-generated `idempotency_key` in the payload; the relay retries `EsignInternal.CreateSigningSession`. Also absent from §4 — nothing subscribes. Billing writes it in the same transaction as `APPROVED → SIGNING`; contract-service writes it with **no status change at all** (D14e), and the outbox is still correct there because APR-07 requires the user's send action to survive esign-service being down. Calling esign synchronously and committing after was rejected: a crash between the two leaves a session that sends to the provider for a document still `APPROVED`, then delivers a callback §9 has no transition for.
  **Second use, same table (D4):** contract/pricing/billing also write `event_type = 'workflow.start_requested'` rows here, one per submit, in the same transaction as the local status commit. `payload` **must** include a freshly-generated `idempotency_key` at creation time — generated once, never regenerated on retry. Its "publish" target is a gRPC call (`WorkflowInternal.StartInstance(..., idempotency_key)`), not the broker, and this event type never appears in §4's event catalog since nothing subscribes to it.
  Exact poll/claim SQL, the cancel-vs-dispatch handoff algorithm, and why a stale claim must never be cancelled directly (timestamp leases have no fencing): [mechanics.md §M2](mechanics.md#m2--outbox-relay-dispatch-and-cancellation-d4-d6).
- **processed_event** (only in consumers): `event_id uuid PK, processed_at`. Still required under Kafka: offsets are committed *after* processing, so a consumer that dies mid-batch re-reads records it already applied.

## 9. Allowed state transitions

`(from → to)` with trigger; trigger kinds: **U**=user action, **W**=`workflow.completed` outcome (D3), **E**=`esign.session_completed` (D10), **S**=scheduler (D14d).

**Every transition in the tables below writes one `status_history` row in the same transaction as the status column update** (D17), carrying `trigger_kind` = the letter in the Trigger column. A status change with no history row is a bug; the two are reconcilable by construction.

**CONTRACT / ADDENDUM**
| From | Trigger | To |
|---|---|---|
| DRAFT | U submit (CTR-02 checks) | SUBMITTED |
| DRAFT, SUBMITTED, UNDER_REVIEW | U cancel¹ | CANCELLED |
| SUBMITTED | W first step activated¹ | UNDER_REVIEW |
| UNDER_REVIEW | W APPROVED / REJECTED / REVISION_REQUESTED | APPROVED / REJECTED / REVISION_REQUESTED |
| REVISION_REQUESTED | U update | DRAFT |
| REJECTED | U revise (explicit action, CTR-04) | DRAFT |
| APPROVED | S effective date (CTR-05)² | ACTIVE |
| ACTIVE | S end date² | EXPIRED |
| ACTIVE | U controlled cancel (CTR-06, D14a) | CANCELLED |

¹ `DRAFT → SUBMITTED` commits **first**, together with an `outbox` row requesting the workflow start (`event_type = 'workflow.start_requested'`, §6), in one local transaction (D4). A background dispatcher retries `WorkflowInternal.StartInstance` until it succeeds — never the reverse order, since a remote success followed by a failed local commit would orphan a live, activated workflow instance on a document still `DRAFT`. While dispatch is pending, the document is genuinely `SUBMITTED` with no instance yet (UI: "Submitted — workflow initialization pending," not an error). SUBMITTED → UNDER_REVIEW is separately event-driven: the owner service consumes `workflow.instance_started` (§4) and flips the status once the instance actually exists and its first step has activated. **Order-tolerant, deliberately:** a `workflow.completed` that arrives while the document is still `SUBMITTED` — possible if `instance_started` was delayed in the outbox past the whole approval, since Kafka orders sends and not commits (D2) — applies the skipped `SUBMITTED → UNDER_REVIEW` first and then the outcome, in the same transaction, rather than rejecting a transition §9 has no edge for. Without this the document wedges permanently on a reorder or a redelivery; with it, both events are idempotent in either order. This also keeps the requirement's `Submitted → cancel` edge real: cancel runs the retry-until-resolved algorithm in §6 (atomic `outbox` cancel only if truly never claimed; otherwise `WorkflowInternal.CancelInstance`, retrying on `NOT_FOUND` — and if the claim is stale rather than fresh, forcing the dispatch to resolution itself before retrying, never assuming a stale claim's owner is dead). The document stays SUBMITTED/UNDER_REVIEW until one branch definitively resolves — never flipped to CANCELLED on an inconclusive read — so there is no window where a workflow instance starts after the document was already cancelled. Once resolved, the owner sets CANCELLED (or the cancel action fails outright if a step was already actioned, `FAILED_PRECONDITION`). **`UNDER_REVIEW → CANCELLED` is reachable only through this handoff**, and only once `CancelInstance` has actually succeeded — i.e. before any approval action was taken on the instance. It is not an unconditional manual transition: a user may not cancel a document out of review by hand, and the owner service must never apply the edge without the round trip that earned it. Where the dispatch intent is missing and there is therefore no `idempotency_key` to verify against, the cancel is refused rather than applied locally.
² Addendum specifics: when an addendum flips ACTIVE (at its `effective_from`), contract-service applies its effects to the parent row **in the same transaction** (system action, audit-logged — not a CTR-07 violation, it applies an *approved* addendum): `TERM_EXTENSION` ⇒ `contract.valid_to = new_valid_to`; `PAYMENT_TERMS` ⇒ `contract.payment_term = payment_term_override`. `ContractInternal.GetContract` always returns these stored effective values (what billing snapshots). Addenda have no own end date — they share the parent contract's expiry.
³ Sending for e-signature (D10, optional, manual, only from APPROVED) does **not** appear in this table — it never changes contract/addendum status. It starts a `signing_session` in esign-service, a fully separate state machine (5.5 "không trộn lẫn trạng thái phê duyệt và trạng thái ký" — D14e). `APPROVED → ACTIVE` above fires on schedule regardless of whether a signing session exists, is in progress, or completed. Contract-service does not consume `esign.session_completed` and has no dependency on esign-service at all (§4) — the **frontend** composes the document-detail view itself, calling `GET /contracts/{id}` (this service) and `GET /signing-sessions/by-document/{document_type}/{document_id}` (esign-service, a new user-facing endpoint) independently through the gateway. Both stay REST, not gRPC: this is user traffic through the gateway, outside D16's internal-only scope.

**PRICE_LIST (version)**
| From | Trigger | To |
|---|---|---|
| DRAFT | U submit⁵ | SUBMITTED |
| SUBMITTED | W APPROVED³ / REJECTED | APPROVED / REJECTED |
| REJECTED | U revise (PRC-06) | DRAFT |
| APPROVED | S valid_from | EFFECTIVE |
| EFFECTIVE | system: successor activates (PRC-04) | SUPERSEDED |
| EFFECTIVE | S valid_to | EXPIRED |

³ Approving a successor version truncates an overlapping predecessor **in the same transaction** (`predecessor.valid_to = successor.valid_from − 1 day`, PRC-04's "hết hiệu lực theo ngày" arm) — otherwise the PRC-03 exclusion constraint would reject the successor's APPROVED flip. Ranges of ever-effective versions are thus non-overlapping, which also makes historical effective-at-date lookups unambiguous.

**PAYMENT_STATEMENT**
| From | Trigger | To |
|---|---|---|
| DRAFT | U calculate | CALCULATED |
| CALCULATED | U edit (controlled, 4.6) | DRAFT |
| CALCULATED | U reconcile | RECONCILED |
| RECONCILED | U submit (PAY-04 checks)⁵ | SUBMITTED |
| SUBMITTED | W APPROVED / REJECTED / REVISION_REQUESTED | APPROVED / REJECTED / REVISION |
| REJECTED, REVISION | U update / revise⁴ | DRAFT |
| APPROVED | U send e-sign (PAY-06, D10) | SIGNING |
| SIGNING | E SIGNED | SIGNED |
| SIGNING | E FAILED/CANCELLED (PAY-07) | REVISION |
| SIGNED | U publish | ISSUED |
| APPROVED, SIGNED | U controlled cancel (PAY-05, D14c) | CANCELLED |

⁴ `REJECTED → DRAFT` and `CALCULATED → DRAFT` are documented deviations — see D14(f) in the plan.
⁵ Same commit-then-dispatch ordering as CONTRACT/ADDENDUM footnote ¹ (D4): local status commits first together with an `outbox` row; a background dispatcher retries the workflow-start call until it succeeds. Applies here too since this is a general rule (D4), not contract-specific.

**SIGNING_SESSION:** PENDING_SEND →(sent to provider)→ SIGNING; **PENDING_SEND or SIGNING** →(provider callback)→ SIGNED | FAILED (PENDING_SEND is accepted so a callback that overtakes the send-response commit is still applied, not discarded); PENDING_SEND →(S, send retries exhausted, default 3 attempts)→ FAILED; PENDING_SEND/SIGNING →(U cancel, `esign:cancel`)→ CANCELLED. Every one of these writes a `status_history` row.
**OPERATION_PERIOD:** OPEN →(U lock, OPS + permission)→ LOCKED. No unlock; post-lock edits require `volume:edit_locked` permission and are audit-logged (4.5).

## 10. Cross-cutting reference values

- **Service groups** (contract.service_group, price_list scope; from Figma): `STEVEDORING, WAREHOUSING, TRANSPORTATION, CONTAINER_HANDLING`.
- **Units** (service catalog; from Figma): `TEU, tonne, trip, day, set`.
- **Addendum change types** (Figma): `UNIT_PRICE_CHANGE, TERM_EXTENSION, ADDED_SERVICE, PAYMENT_TERMS`.
- **Billing cycle** (contract): `MONTHLY` (only value in scope; column exists for future cycles).
- **Statement line source:** `CALCULATED, MANUAL` (reconciliation panel "Manual adjustments").
- **Currency:** `VND` default.
- **Permissions (seed).** Format `resource:action`. **Separator rule: `:` = permission, `.` = event type** (§4) — the two vocabularies never look alike.

  | Resource | Permissions |
  |---|---|
  | customer | `customer:read`, `customer:write` |
  | contract | `contract:read`, `contract:write`, `contract:cancel_active` |
  | addendum | `addendum:read`, `addendum:write` |
  | pricelist | `pricelist:read`, `pricelist:write` |
  | volume | `volume:read`, `volume:write`, `volume:lock_period`, `volume:edit_locked` |
  | statement | `statement:read`, `statement:write`, `statement:cancel_approved` |
  | approval | `approval:act` |
  | esign | `esign:send`, `esign:cancel` |
  | notification | `notification:read` |
  | admin | `user:manage`, `workflow:configure`, `doctype:configure`, `audit:view_all` |

  **Splitting test.** `write` covers all ordinary mutation of a document in a state where mutation is allowed — including submit, which needs no code of its own (no role holds `write` without it). A separate permission is justified **only when a different set of people should hold it**. The four that qualify all license an act the state machine otherwise forbids: `contract:cancel_active` (CTR-06 — an ACTIVE contract can't be written at all), `statement:cancel_approved` (PAY-05, same), `volume:edit_locked` (4.5's *"quyền đặc biệt"*, overrides a lock), `volume:lock_period` (irreversible and system-wide, not per-record). Anything else that is "write under a different name" is noise.

  **Code checks permissions, never roles.** `if (hasRole(SALES_MANAGER))` is the same hard-coding §4.7 forbids one layer down — it would make "add a role" a redeploy, contradicting §2's runtime *"phân quyền"*. Roles are bundles (§7); only permission codes appear in code.
  `approval:act` grants the *ability* to act on steps in general; whether the caller may act on **this** step is `step_assignee` in workflow-service (APR-01) — a permission string cannot express per-object context (D11 layer 2).

Traefik routes `/api/v1/{resource}` → owning service (stripping `/api/v1`), rate-limits, terminates TLS, **and validates the access-token signature** via the `agilezebra/jwt-middleware` plugin, then **injects the identity as trusted headers** (`X-User-Id`, `X-Username`, `X-Full-Name`, `X-Department`, `X-Roles`) and strips client-supplied copies. **Services trust the headers** — `HeaderAuthenticationFilter` in `libs/common` reads them and resolves permissions from the Redis map (fail-closed); services hold no JWT code or keys (`JwtVerifier`/`JwtProperties`/`jjwt` removed from `libs/common`). We deliberately chose gateway-centric auth over per-service re-validation: without a service mesh the zero-trust argument is theoretical, and one validation point is simpler. The cost — the internal network must be sealed (services publish no host ports; the edge is sole ingress) — is accepted and is a K8s NetworkPolicy in prod. `api-gateway` is dropped as a Java service; the edge is infra (`infra/docker/traefik/`, compose labels). **(2) RS256, not HS256.** identity signs with an RSA **private key** (`infra/keys/jwt-private.pem`, gitignored + mounted); the edge validates with the **public key** (committed, inlined in `infra/docker/traefik/dynamic/jwt.yml`). The signing secret lives in exactly one place. **(3) JWT blacklist removed; two-token flow (OAuth 2.1 / RFC 9700 standard).** Login issues a 15-min access JWT + a 14-day opaque refresh token, SHA-256-hashed and stored in the new `pas_identity.refresh_token` (id, user_id, family_id, token_hash, issued_at, expires_at, revoked_at, replaced_by). `POST /auth/refresh` **rotates** (new access + new refresh, old revoked) with **family-based reuse detection** — replaying a revoked refresh token revokes the whole family. Logout revokes the family; disabling a user revokes all their families. Revocation moved off any per-request lookup onto the ~15-min refresh path (≤15-min lag), which is what makes the stateless-access-token design coherent. - 2026-08-29 — **`document.expiring` gets a derived `event_id` and mirrors it into a header; the D9 "no outbox row" argument had a hole in it.** D9 justifies skipping the outbox for this event because a lost warning re-fires on the next sweep — true, but the Kafka ack and the `last_expiry_warning_for` stamp cannot be made atomic, so a crash between them re-sends, and two replicas sweeping at once can both send before either stamps.
